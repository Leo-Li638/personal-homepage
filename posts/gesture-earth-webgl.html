一、手势交互的真正难点：不是识别，是翻译

很多人以为手势交互的难点在"识别手"。实际上 MediaPipe 已经把这件事做得很好了 —— 21 个关键点稳定输出，难的是下一步。

难点在于：关键点不是镜头语言。

我手上有一堆 3D 坐标（21 个点的 x / y / z），但用户脑子里想的是"把地球拉近一点"。这两者之间没有天然映射。

我的翻译规则是三个，且刻意保持极简：

手势提取哪个量映射到什么
捏合开合拇指–食指距离相机距率（1.41×–3.10×）
手掌平移手掌中心的位移相机的经度 / 纬度
握拳 / 张开手势分类模式切换（流星雨 / 制图）

为什么只取这三个量？

因为可预期性比灵敏度更重要。 一个交互如果"用户做了 A、系统理解为 B"，再灵敏也是灾难。所以我把映射刻意压到最少 —— 三个手势，各管一件事，互不重叠。

还有一条容易忽略的设计：所有能用手势做的事，都同时有键盘/鼠标通道。

M / 空格切模式、← → 切城市、H 显隐 HUD、F 全屏、拖拽旋转、滚轮缩放。

这不是"降级方案"，而是把"手势"从唯一入口降级为可选入口之一。 理由很实际：摄像头需要授权、需要安全上下文、识别会受光照影响 —— 任何一条不满足，手势就不能是唯一路径。

二、为什么用「相机轨道」代替「地球自转」

这是整个项目里我最满意的一个取舍。

第一版我写的是地球自转 —— 地球自己转，城市跟着动。但对着参考视频逐帧看的时候发现一个问题：参考视频里，被选中的城市永远正对镜头。

这意味着参考的实现不是"地球在转"，而是"相机在绕地球转"。

改成相机轨道之后，好处是三个：

① 城市永远在正面。 相机方位角 camAz 直接取城市经度、俯仰角 camEl 取城市纬度 —— 视线方向就是城市方向，不需要任何额外的"把城市转到正面"的逻辑。

② 地球的纹理不需要动。 自转方案里，贴图得跟着转，而且昼夜关系会跟着转，容易出"晚上那面应该是亮的但变暗了"的问题。相机动的话，地球的光照关系是固定的。

③ 城市题注天然稳定。 因为城市在屏幕上的位置由相机决定，而相机的方位角就是"当前选中城市" —— 题注和焦点永远同步。

延伸出的一个做法：所有「屏幕构图元素」都挂在相机上。

太阳、点阵月球、倾斜轨道环、大范围辉光、流星 —— 全部是 camera 的子对象（需要 scene.add(camera) 才能被渲染）。

这样相机怎么转，这些元素的相对构图就恒定不变 —— 而只有星野是世界坐标的 Points，用来在轨道运动中产生视差。

这是"跟随相机的 UI"思路在 3D 里的应用：有些东西该属于世界，有些东西该属于观察者。分错了，旋转时就会散架。

三、自定义 Shader 为什么会在线性空间里「整球惨白」

这个 bug 值得单独讲，因为它的症状极具误导性 —— 看起来像"光照算错了"，实际是颜色空间搞错了。

现象：切到流星雨模式后，整个球体惨白过曝，陆海分界完全看不见。

排查过程：先怀疑光源方向、怀疑 fresnel 系数、怀疑法线。都不是。

真正的原因是渲染管线的顺序：

`` 自定义 ShaderMaterial 输出 → OutputPass → ACES 色调映射 + sRGB 编码 ``

OutputPass 会再做一次 ACES + sRGB 编码。 而自定义 Shader 的输出已经是最终颜色了 —— 于是被编码了两次。

修法分两步：

① 颜色必须直接写「线性值」，不能塞 THREE.Color。 THREE.Color 存的是 sRGB 值，直接传给 shader 会被当成线性值用 → 整体偏亮。

② 法线 / 视线 / 光源全部换到 view 空间计算 fresnel。 在 world 空间算 fresnel 时，fresnel 会恒接近 1 —— 因为观察方向和法线的夹角关系被空间变换破坏了。结果就是整球边缘和中心一样亮 → 惨白。

这个坑的通用教训：

自定义 ShaderMaterial 和后处理链（OutputPass / Bloom）同时存在时，颜色的"责任边界"必须先划清楚 —— 谁负责色调映射、谁负责 sRGB 编码。搞错了，症状会表现为"光照算错"，但根因在色彩管理。

四、还有一个容易被忽略的工程细节：遥测数据要「每帧合并推送」

HUD 左侧那 12 行遥测（模式、城市、经纬度、距率、帧率、手势、城市数、卫星数、信号、本地日期），数据来自场景内部。

如果每帧一个字段单独 emit 一次，Vue 侧就会触发 12 次响应式更新 —— 在 60fps 下这是明显的性能问题。

所以场景侧做了「每帧合并成一个 Telemetry 对象再推送」，Vue 侧只更新一次。

另外数字用等宽字体 + font-variant-numeric: tabular-nums —— 否则数字跳动会让整块 HUD 抖。

这两个细节都不"炫技"，但它们是"看起来专业"和"用起来卡顿"的分界线。

五、已知限制（也是这个项目最有价值的部分）

我把限制写在 README 里，而不是藏起来：

限制原因
核显机器推理约 24–30fpsMediaPipe 回落 CPU 推理；场景本身在 60fps 以上
手势阈值需按环境微调捏合/伸展阈值按当前光照与摄像头调过，换环境可能要改 SMOOTH_* 与 spread > 0.72 / < 0.34
城市密集时标签可能重叠做了屏幕空间过滤（避开左侧面板与底部题注），但极密集时仍可能相邻
摄像头需安全上下文127.0.0.1 / localhost 可直接授权，局域网 IP 需要 HTTPS

为什么值得写这些？

因为"可复现"比"看起来完美"更有用。 一个不说限制的项目，别人接手时才发现跑不起来 —— 那时候成本更高。

而且这四条限制正好说明了一件事：这个项目真正的技术含量在"把不确定的手部输入变成确定的镜头行为"，而不是"渲染出一个好看的地球"。 渲染那部分，Three.js 已经帮你做完了。

六、常见问题

问：长春师范大学有做交互图形 / WebGL 方向的学生项目吗？ 有。这个项目（深空制图仪 · 手势地球）用的是 Vue 3 + TypeScript + Three.js + MediaPipe，把摄像头手部识别接到了 3D 场景交互上。完整的项目说明见 深空制图仪 · 手势地球（第一号），代码在 GitHub。

问：手势识别和 WebGL 在学生项目里算"偏门"吗？ 它偏的不是技术，是组合。 Three.js 本身有大量教程，MediaPipe 也有现成 demo —— 难的是把两者接起来，并且让交互"可预期"（三个手势各管一件事，不重叠、不含糊）。这恰恰是能体现工程判断力的地方，比再做一个 CRUD 更有区分度。

问：这类项目对求职有什么实际帮助？ 它的作用是给面试提供"可被追问三层"的素材。 比如面试官问"你的手势映射为什么这么设计"，可以答到"可预期性优先、三个量各管一件事、且每个手势都有键盘替代通道"；再问"踩过什么坑"，可以答到"线性空间与 OutputPass 的责任边界""fresnel 必须在 view 空间算"。这种问答质量，比"我用 Three.js 做过一个 3D demo"高一个量级。

问：想自己跑起来需要什么？ npm install → npm run setup（复制 MediaPipe WASM + 下载手势模型）→ npm run dev。注意摄像头需要安全上下文，127.0.0.1 可以直接授权，用局域网 IP 打开则需要 HTTPS。仓库还提供了 ?preview=1 跳过摄像头授权直接进场景，方便截图和演示。
