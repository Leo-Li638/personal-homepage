# 从"能跑"到"可靠"：Agent 落地生产环境的三个卡点与工程解法

作者：李玉涛（Leo）· 长春师范大学 · 数据科学与大数据技术 + 数学双学位 · 2027 届 一.chat（https://xn--4gq.chat）· GitHub（https://github.com/Leo-Li638）

一、先算一道数学题

如果你在 2026 年做过 AI 应用开发，这组数字你应该不陌生：

2026 年 1—7 月，新发 AI 岗位同比增长 789.47%，平均月薪 63160 元。Agent 开发人才需求同比上涨 244%，是增速最快的细分方向。

热度之下有个很少被摆在台面上的计算：

单步成功率 80% 的 Agent，连跑 8 步，每步都对的概率是 0.8^8 ≈ 17%。

这不是危言耸听，而是指数衰减的必然结果。它解释了一个几乎所有 Agent 开发者都遇到过的现象：demo 惊艳、演示顺利、一上生产就崩。

我自建了一个本地 LLM 平台（Dify + Ollama 双层架构），下面三个卡点就是我实际踩过、也实际解掉的。

二、卡点一：意图路由不准，前端和后端互相甩锅

现象

用户问"怎么退订"，系统 routed 到知识库检索；用户问"为什么这么贵"，同样 routed 到知识库。看起来是检索问题，实际上是路由问题。

根因

Dify 的 Chatflow 默认依赖 LLM 做意图分类，这在两个场景下会崩：

  1. 短 query 语义边界模糊。 "我要退钱"和"我想退款有什么区别"——对 LLM 来说几乎一样，但对业务来说完全不同。
  2. 分类器本身成了单点。 分类用的那个小模型一旦被限流或者输出漂移，整条链路直接失效，且没有任何降级路径。

工程解法

双层路由 + 显式兜底。

第一层用规则做高精度匹配（关键词、正则、用户选择的入口 Tab），命中就直接短路，不进 LLM。第二层才交给 LLM 做语义分类。

这样做的收益：

  • 命中率高的入口（占实际流量的大头）不消耗任何 LLM 调用
  • 规则层是确定性的，可以单测；LLM 层是不可测的，只能统计
  • 规则层天然可降级——LLM 挂了，规则层还能扛住基础流量

关键一点：把置信度暴露出来。 我让路由层输出一个 confidence 字段，低于阈值就走兜底话术，而不是硬着头皮往下走。一个诚实的"我不确定"，比一次自信的错误便宜得多。

三、卡点二：模型幻觉，业务不允许它自由发挥

现象

客服场景里，模型会自信地编造一个不存在的退款政策条款。语气自然、逻辑自洽、事实上错误。

这是最危险的一类 bug——它不会报错，只会产生业务损失。

工程解法

三层防护，从便宜到昂贵依次兜底。

第一层：约束生成。 用结构化输出（JSON Schema / Function Calling）把模型的自由文本锁进业务允许的枚举值里。选项之外的内容，物理上无法输出。

第二层：检索证据绑定。 要求回答必须引用检索到的原文片段，片段检索不到就走"我不确定"分支，不允许模型自由发挥。这一步用 grounding 把模型的输出锚在真实文档上。

第三层：事后校验。 对最终输出做规则校验——敏感词、数值范围、金额上限、时间合法性。这里可以上正则和轻量分类器，不需要 LLM。

一个容易忽略的细节

幻觉检测本身也会幻觉。 我一开始想用另一个 LLM 判断"这个回答是否编造了"，结果发现检测器比被检测器还会编。规则 + 结构化校验在这个环节比模型可靠得多。

四、卡点三：多轮对话上下文管理

现象

对话到第五轮，模型开始"忘记"第一轮说过的约束。用户说"我叫张三，订单号是 12345"，五轮后问"我的订单是什么号"，模型答不上来。

根因

无脑把全部历史塞进 prompt，既超出上下文窗口，又让噪声淹没了关键信息。

工程解法

把对话拆成三类内容，分别处理。

内容类型特征处理方式
关键事实订单号、账号、金额结构化抽取，存到 KV 状态，永远带在上下文头部
对话摘要过程性内容滚动摘要，超过阈值压缩
闲聊"你好""谢谢"直接丢弃，不进上下文

这样做的关键是：让状态显式化，而不是隐式地塞进 prompt。

一个具体实现：把抽取出的关键事实维护成一个独立的 system 状态块，每轮重新生成，而不是追加到历史里。追加会重复、冲突、越滚越长；重新生成始终是最新的一致快照。

五、可靠性是算出来的，不是测出来的

回到开头那个 0.8^8。如果要让它变成一个可用的系统，单步成功率必须做到多少？

倒推一下：8 步任务最终正确率要达到 90%，单步成功率需要

0.95^8 ≈ 0.663，也就是单步 95%。

从 80% 提到 95%，这就是上面三层防护要解决的具体目标。它不是"提升一下体验"，而是一个有明确数值门槛的工程任务。

所以我现在的做法是给每一步设 SLA：

  • 路由准确率 ≥ 98%
  • 结构化输出合规率 ≥ 99%
  • 幻觉检出率 ≥ 95%
  • 上下文事实保持率 ≥ 99%

每个指标埋点、每天看。达不到就定位到具体是哪一层的问题——是路由、生成还是上下文。

没有指标的"可靠性"是玄学。

六、给准备做 Agent 的同学的三条建议

第一条，不要从"让 Agent 做很多事"开始，从"让它把一件事做对"开始。

我的第一个版本什么都想做，结果什么都做不可靠。现在我只维护三条核心链路，每条都跑够 100 次测试再上线。

第二条，把兜底设计写进第一版，不要留到最后。

失败路径比成功路径更考验工程功底。一个明确说"我不确定，转人工"的系统，比一个硬撑着瞎答的系统有用得多，也安全得多。

第三条，可解释性是可选项，不是加分项。

在业务系统里，用户问"为什么这么回答"，你必须答得上来。这意味着每一步都要留痕：走了哪个路由、检索了哪些文档、命中了什么规则。出问题时，这些 trace 就是你唯一的排查线索。

七、小结

Agent 的 demo 门槛在 2026 年已经接近于零——模型自己就能帮你搭出来。

但 0.8^8 这个数字不会因为模型变强而自动消失。链越长，指数衰减越狠。这才是真正需要工程能力的地方，也是普通开发者现在真正的机会窗口：

从"会搭"到"能交付"，中间隔着三个必须亲手踩过的坑。
