# AI 包办了 40% 的代码起草，最强 Agent 却只做得对 10.8% 的真实任务

先说清楚这是什么 2026 年 10 月 28 日，GitHub 发布 Octoverse 2026 年度报告。 2026 年 10 月 27 日，Surge AI 发布 DAYJOB: Tax 评测基准。 这两份东西隔了一天发布，但放在一起看，是今年最锋利的一组对照。 我是长春师范大学一名 2027 届在校本科生，数据科学与大数据技术专业，辅修数学，Java 后端在读，同时自己搭了一个本地 AI 平台（Dify + Ollama + DeepSeek）。所以下面写的，是一个正在用 AI 写代码、同时在学怎么不被 AI 取代的人，把这两份报告读完之后逼自己回答的问题。 文中所有数据均标注来源与发布时间，版权归原作者所有。

---

一句话版

AI 已经会写代码了，但它还不会「发现该写什么」。 GitHub：2026 年 9 月，超过 40% 的 PR 以 AI 智能体起草的初稿开头（3 月只有 17%）。 Surge AI：最强的 Agent 在 50 个真实税务任务上只通过 10.8%（pass@1，95% 评分阈值）。 这 40% 和 10.8% 之间那道缝，就是 2027 届最该练的东西——Issue Spotting：先发现该问什么问题，再回答它。 我把它翻译成一句求职能直接用的话：当写代码变成免费，你的价值从「能把需求变成代码」迁移到「能判断需求对不对、结果够不够格」。

---

一、两份报告，两个数字

报告 A：GitHub Octoverse 2026（10 月 28 日发布）

统计窗口是 2025 年 10 月 1 日到 2026 年 9 月 30 日。几个关键数字：

指标数值
9 月以 AI 智能体初稿开头的 PR 占比超过 40%（3 月为 17%）
9 月 agent 发起的 PR 数量1.1 亿个，约为 3 月的 6 倍
agent PR 中改动多个文件的比例87%（非 agent PR 为 79%）
agent PR 两周内合并率9 月 90%（2 月为 83%；非 agent 组约 86%）
全平台年度提交量179 亿次 push、343 亿次 commit、13 亿个合并 PR

GitHub 对「agent 发起的 PR」的定义是：首个草稿来自一个可检测到的编码智能体的 PR——哪怕人后来改写了其中一部分，也仍然计入。

平台整体也涨得离谱：合并 PR 从 2024 年的 4.02 亿、2025 年的 5.38 亿，涨到 13 亿。开发者总数 2.25 亿。Copilot 月活里使用智能体功能的比例从一年前的 35% 升到 55%，云端 agent 使用量同比 +230%。

这组数字看起来像个大胜利。但有三个限定条件必须一起读：

  1. GitHub 自己也说这是「下限」 —— 只能统计它检测到的智能体活动，检测不到的不算，人在人类 PR 里顺手用 AI 也不一定算。
  2. 合并率不是质量指标。 报告没有给出 agent PR 和非 agent PR 的缺陷率、安全结果或长期维护成本对比。「90% 两周内合并」只说明它合得快，不说明它合得对。
  3. 这些是观测数据，不是受控实验 —— 没有控制任务难度、团队习惯和代码正确性。

不过有一条语言维度的数据，求职党必须盯住：

语言合并 PR 中检测到的 AI 参与率
TypeScript44.1%
Python41.1%
Rust40.4%
Java21.2%

Java 只有 21.2%，不到 TypeScript 的一半。

另外几个值得记的：付费 Copilot 用户在 9 月用了 47 个不同的模型，没有一个占比超过 25%；61% 明确自己选模型的用户用了不止一个模型。

报告 B：DAYJOB: Tax（10 月 27 日发布，Surge AI）

这个基准的设计很不一样。它不是给你一道题让你答，而是给你一个客户的文件夹，让你去做一个税务从业者该做的完整工作。

  • 50 个真实税务工作环境，覆盖个人、小企业、合伙、财产投资、遗产赠与、跨境、税务争议等 8 个执业领域
  • 1,789 个工作区文件，中位数每任务 30 个、最多 123 个：1,487 个 PDF、117 个 Excel、38 个 Word，还有邮件、图片、CSV、JSON
  • 题目由有 PwC / 德勤 / 普华永道 / Baker Tilly 背景的税务专家出题并评审
  • 计分方式：pass@1，且必须满足该任务至少 95% 的评分标准（涵盖计算、支撑证据、关键问题识别、交付物完成度）

成绩：

模型通过率
Claude Sonnet 5.510.8%
Claude Fable 5.19.6%
Claude Opus 5.59.2%

十次里有九次过不了专业复核。 Surge AI 自己的结论是：智能体「还没通过审计」。

把两个数字放一起

`` GitHub：40% 的 PR 由 AI 起草 ↓ 生成的边际成本 → 0 ↓ DAYJOB：真实专业任务通过率 10.8% ``

生成侧已经普及，完成侧几乎没动。

这个剪刀差就是 2026 年 10 月最重要的信号。而且它比「AI 会不会取代程序员」这个问题有用得多 —— 因为它直接告诉你该往哪个方向长。

二、差距到底在哪：Issue Spotting

DAYJOB 报告里最值得抄的不是分数，是失败模式。它精准地命名了一件事：Issue Spotting（发现问题）。

案例一：算对了，但漏了一个悬崖

任务：Anna 要卖公寓。她 2024 年 8 月已经搬出，想知道 2026 年 10 月还是 2027 年 1 月过户更划算。

Agent 的表现（不错）：正确判断两个过户日期都满足「过去五年住满两年」的居住要求，最高可豁免 25 万美元的资本利得。计算完全正确。

Agent 漏掉的（致命）：因为 Anna 2024 年 8 月搬出，她大约在 2027 年 8 月底就不再满足居住要求。如果过户拖到 2027 年 8 月之后，她可能丧失豁免资格。

跨 5 次运行：Opus 5 次全部识别出这个截止日期；Astra 5 次全部没识别出来。

注意这个错误有多阴险：它不是一个计算错误，它是一个「问题本身没被提出来」的错误。如果 Anna 没主动问这件事，agent 的回答在它自己的评价体系里是完全正确的。

案例二：默认了不该默认的前提

任务：给一对正在分开的夫妇提供退休账户处理建议。

多个模型一致假设这对夫妇未婚，尽管案卷里有记录显示可能存在来自另一州的有效婚姻。

Opus 5.5 在 5 次运行中全部去核查了婚姻状态；另一个模型 5 次里查了 4 次。

「去查一下」这个动作本身，就是被测的能力。

提炼：两种能力，两种考法

通用 benchmark 测的DAYJOB 测的
题目已经给你了你得自己找到
能力求解能力发现问题的能力
失败长相算错压根没意识到有这个问题
类比考试题真实工作

而 Surge AI 引用的另一组数据说：90% 的美国工时没有 AI benchmark 覆盖。

这解释了一个长期存在的悖论：为什么模型在各类榜单上分数越来越好，但一进真实场景就频频翻车？

因为榜单考的是「回答得好不好」，而真实工作考的是「问得对不对」。 你的产品经理、你的老板、你的客户不会给你一道题。他们会给你一堆半成品、几份互相矛盾的材料、和一个没人明说的目标。

AI 在前者已经接近饱和，在后者还不及格。

三、这对你的择业意味着什么（这是本文最实用的部分）

3.1 「写代码」这个能力，贬值了——而且贬得很快

GitHub 那个 40% 意味着：到 2026 年 9 月，你写代码这项技能在公共代码库里的边际价值，已经被 Agent 吃掉了四成。

这对你意味着两件相反的事：

坏消息：简历上写「熟悉 Java / Python」，竞争力在贬值。面试官看到「会用 AI 写代码」，反应已经从 2024 年的「加分」变成 2026 年的「这谁不会」。

好消息：代码本身从来就不是最值钱的部分。 你真正做过的项目里——设计了什么模型、为什么这么选、踩了什么坑、怎么验证的——这部分一分钟都没被 Agent 替代。

3.2 但有个例外，而且它对你极其有利：Java 只有 21.2%

这是我读完 Octoverse 后最想告诉你的一条。

TypeScript 44.1%、Python 41.1%、Rust 40.4%，Java 21.2%。

Java 的 AI 渗透率不到 TypeScript 的一半。这不是「Java 更难」，而是两个更现实的原因：

  1. 存量系统太老。 企业 Java 库里大量是运行了十年以上的单体系统，Agent 的上下文窗口和训练语料对这类代码的覆盖极低。
  2. Agent 的产出在 Java 生态里更难自动落地。 Java 的构建、依赖、部署链路比前端更依赖人工判断。

对你的直接推论：

  • 「Java 后端 + AI 辅助」这个组合，在 2027 届的相对稀缺性是高于「Python/前端 + AI 辅助」的。
  • 但更重要的推论是：Java 21.2% 的低渗透，恰恰说明 Java 领域「AI 辅助红利」还没被吃干净。 前端同学已经接受了「AI 写 44%」这个新常态并且在往「怎么用 AI」的方向卷；Java 领域的大部分人还没开始卷这件事。

换句话说：你在 Java 后端 + AI 应用这个交叉点上，还有一段没人抢的路。

顺带说，你学 Java 也不只是为了就业。Java 后端那种「显式、强类型、可测、可部署」的工程约束，恰恰是训练 Issue Spotting 的好场景 —— 因为它逼着你面对真实的类型系统、真实的异常边界、真实的联调问题。Python 里 try/except Exception: pass 能糊过去的事，Java 编译不过。编译器是一层免费的 Issue Spotting 训练器。

3.3 你的数学和数据背景，在这件事上是主场不是辅科

这里我要说得直接一点，因为很多人会误判。

Issue Spotting 的本质，就是「在不完备的信息里识别出那个没被提出来的问题」。 这件事需要的不是写代码能力，是：

  • 知道一个系统的正常形态长什么样（才能看出哪里不对）→ 这是建模能力
  • 量化「多大概率会出事」（才能判断这个异常值该不该管）→ 这是概率统计
  • 从异常数据里反推可能的原因（而不是记录现象）→ 这是数据分析
  • 在多个解释里挑一个可验证的 → 这是假设检验

这四样，正好是数据科学 + 数学双学位的完整训练内容。

而且 DAYJOB 那个「算对了但漏了截止日期」的案例，正是纯数学专业最容易犯、纯计算机专业不容易犯的错误类型：数学训练会让人把「给定的问题」解得非常漂亮，而训练「发现没被给定的问题」需要的是领域建模直觉。

这里我要给一句反直觉的判断，但我不确定它完全成立：很多人以为学 AI 编程是往「会写代码」的方向挤，其实往反方向挤才对——往「懂一个领域到底在干什么、哪里最容易出错」的方向挤。

前者是红海且在贬值，后者是蓝海且在升值。

3.4 三个可迁移的「问题清单」

我把 Issue Spotting 翻译成你能立刻用的形式：每个领域都有一张「该主动检查什么」的清单。

举三个例子，都是你在做的项目里真实存在的：

做学情推题（SmartClass）时，Issue 清单是：

  • 掌握度估计的样本量够不够？某个知识点只做过 2 道题，我的拉普拉斯平滑参数选多少？
  • 遗忘曲线的衰减对不同学生该用同一条曲线吗？（有人考前突击，有人长期稳定）
  • 题目难度和掌握度是不是混淆了？（答错是「不会」还是「这题太难」）
  • 推给学生的题会不会超纲？超纲题测出来的掌握度是假的

做 AI 平台（燎原火）时，Issue 清单是：

  • 意图路由置信度落在灰区时，系统在干什么？（这正是我上次那篇文章写的降级链路）
  • 幻觉防护的规则本身有没有覆盖不到的输出形态？
  • 多轮上下文里，第 7 轮的否定句还在不在？（这个 bug 我真踩过）
  • 用户没说出来但想要的东西，我的系统能 infer 吗？

做订单系统（OrderBoss）时，Issue 清单是：

  • 重复提交（用户网络卡了点了两次）——幂等做了吗？
  • 并发下单同一商品库存不够——锁加对了吗？
  • 金额计算的精度和舍入规则在前后端一致吗？
  • 退款流程和订单状态机会不会进入非法状态？

这三个清单的共同点：它们都不是「写代码」任务，是「想清楚」任务。 而想清楚，正是 AI 现在最不擅长的（10.8% 那部分）。

你只要能把自己领域里的这张清单建起来，你就在做 Agent 现在做不了的事。

四、三个可以这周就做的动作

动作 1：给你正在做的每个项目，写一份「Issue 清单」

不是 README，不是技术栈列表，是一份「这个地方最容易出问题」的清单，10 条以内。

写的时候你会有两个发现：

  1. 你会发现你之前没想清楚的地方比你想的多 —— 这份清单本身就是学习产出；
  2. 你会发现很多条是 AI 提不出来的，因为它不知道你的业务约束 —— 这就是你的护城河的具体形状。

面试时这份清单比任何技术栈描述都有用。 「我做的学情推题模块，最容易出错的是掌握度估计在低样本下的失真，我用拉普拉斯平滑 + 最小样本门槛处理，误差控制在 X」——这句话里有判断、有取舍、有验证，比「熟悉机器学习算法」强十倍。

动作 2：给 AI 的产出加一道「Issue Spotting 层」

这一步是把概念变成工程。

你现在的用法多半是： 描述需求 → AI 生成 → 我看看能不能跑 → 差不多就收工。

升级后的用法： 描述需求 → AI 生成 → 我先列出「这份产出应该在哪几个地方出问题」，再去 review。

具体做法，就是我上次那篇讲的意图路由灰区反问的同构物：在 AI 交付之前，先让它（或你自己）回答「这个结果最可能在哪出错」。

我自己的实践是：让 AI 在交付代码时，必须同时给出「这个实现最可能在哪 3 个地方出错 + 我为什么认为它是对的」。这一步成本很低，但它把 review 从「通读代码」变成了「定向排查」。

而且这一步是可以量化的：review 一次发现的问题数、修复一轮后的残留问题数。你自己也能积累出「哪类 AI 产出最容易在哪错」的直觉 —— 这个直觉，就是 Issue Spotting。

动作 3：把「模型选择」当成设置项，而不是信仰

Octoverse 里那个数据值得反复看：付费用户一个月用了 47 个不同的模型，没有一个超过 25%；61% 主动选模型的用户用了不止一个。

而同期 DAYJOB 里，Claude Sonnet 5.5（10.8%）竟然超过了 Opus 5.5（9.2%） —— 更贵的、更强的旗舰模型，在真实任务上反而输给更小的那档。

这两个事实合起来说的是同一件事：没有哪个模型是「最强的」，只有「对这个任务最合适的」。

所以：

  • 不要在简历或面试里押注某一个模型。 说「我熟悉 XXX 模型」很快会过期（上周刚出的 Mistral Large 4、DeepSeek V4.1、Kimi K3.1 就是例子）。
  • 要说「我有一套按任务选型、按成本和质量验证的方法」。 比如我自己的燎原火为什么本地 Ollama 跑日常、云端 DeepSeek 兜底 —— 这是选型逻辑，不是信仰。
  • 面试时的加分句式：「我不预设模型，按任务类型做 A/B，评估指标是路由准确率和单次成本，不是跑分。」

顺便说，如果你的项目里能用上刚开源的这批模型（Mistral Large 4 是 1 万亿参数原生多模态 MoE、52B 激活参数；DeepSeek V4.1-Flash 是开源权重里 Terminal-Bench 4.0 冲到 42.3；Kimi K3.1 Pro 是 2.8T 总参 / 104B 激活、1M 上下文，11 月 4 日前放出完整权重），那「开源权重可自托管」这件事本身就是一个值得写进项目文档的决策依据 —— 成本、隐私、延迟三个理由任选一个都行。

五、三个反直觉的推论

推论 1：合并速度不是能力指标

Octoverse 最容易被误读的就是那个「90% 两周内合并」。

合并率高，说明的是「它提交得快、人类愿意点合并」，不是「它写得对」。 报告自己都没敢给出缺陷率对比。

对你的启示：在 AI 时代，不要用「产出量」证明自己。 「我本季度提了 30 个 PR」正在贬值，因为 Agent 能把这个数字放大几十倍。要换指标：返工率、线上事故数、接手成本 —— 这三个数字 AI 提不高。

推论 2：密钥泄露率翻倍，说明责任问题没解决

Octoverse 报告里有一个数字被很多人略过（注：这是第三方对报告的分析汇总，不是 GitHub 官方口径）：Claude Code 辅助的公开提交中，密钥泄露比例约 3.2%，大约是 1.5% 基线的两倍。

如果你在做 AI 编程工具，这就是一条真实的产品红线。 AI 生成的代码更容易把硬编码凭据带进提交，因为 AI 是从全网语料里学「怎么写配置文件」的，而全网语料里到处都是硬编码 key 的例子。

这一条对你个人也重要：如果你用 Codex / Claude Code 提交开源项目，加 pre-commit secret scanning 不是可选项。我自己给燎原火加的就是这条。

推论 3：真正稀缺的可能不是「判断」，是「知道该判断什么」

DAYJOB 那个 10.8% 里，Opus 5 次全对、Astra 5 次全错 —— 同一个模型家族，同一个任务，差别只在「有没有想到那个截止日期」。

这说明 Issue Spotting 是可以被「教」的：给了正确的检查清单，模型表现大幅提升；没给，它就想不到。

所以最高杠杆的技能可能不是「更强的判断力」，而是「建立判断清单」的能力 —— 也就是把你的领域知识结构化。

这是一件 2027 届学生现在就能开始、而 AI 短期内抢不走的事。 因为它需要的是「在一堆具体约束里反复踩过坑」，而 AI 没有你的坑。

---

六、这套判断会在哪里失效

我必须说清楚这套逻辑的边界，否则它就只是新的焦虑制造机。

第一，10.8% 是一个特定任务集的极端值，不能外推成「AI 只能做 10% 的活」。 DAYJOB 测的是税务——一个高监管、高责任、极端重视「主动发现未披露问题」的领域。同一个模型在写 CRUD、生成文档、做数据分析时的表现完全不同。看到 10.8% 就以为「AI 不行」，和看到 40% 就以为「AI 全行」一样不专业。

第二，「代码贬值」的结论只在「有明确正确答案的编码任务」上成立。 探索性研究、架构决策、跨系统权衡、把模糊需求翻译成系统设计——这些 AI 现在做不好，而且短期内也不会变好。说「写代码不值钱了」，等于说「执行不值钱了，判断才值钱」，这是过度简化。 执行依然是收入的基础，只是它的定价权在往下走。

第三，Java 21.2% 的低渗透不代表 Java 更安全。 它可能只是说明 Agent 的语料里 Java 老系统太少，也就是Agent 做 Java 存量系统的能力更差 —— 这确实对从业者是好事，但也可能只是暂时的。随着语料补充和工具链成熟，这个数字是会涨的。别把一个季度的高点当成护城河。

第四，「Issue Spotting 能力变成护城河」这个判断可能只对某些职业成立。 如果你的工作就是执行有标准答案的任务（标准化测试、模板化运维、初级文案），那 10.8% 那种专业判断的稀缺性对你没用——你的岗位整体在被压缩，不是因为你不够会判断。 选对行业比练对能力更重要。

第五，如果 AI 的「主动发现问题」能力在一年内突破，逻辑会反转。 DAYJOB 的作者自己说了，这种基准「难以大规模构建」，因为它要求评估者独立知道「这个场景里有哪些问题存在」——这既是它珍贵的原因，也是它稀缺的原因。一旦有人把这类基准规模化，或者模型学会了「先自己列检查清单再干活」，10.8% 这个数会涨。我在自己的项目里已经用「灰区反问」手工做了这件事 —— 如果模型能原生做，那这个技能确实就贬值了。 所以我把它写进失效边界，而不是结论。

第六，我引用的所有数字都是别人的样本。 40%、87%、90%、21.2%、10.8%、3.2% —— 来自 GitHub 官方报告、Surge AI 官方博客和第三方分析，量级可以参考，不能当你的期望值。 你自己项目上的返工率、review 发现率，才是你该盯的数。

七、常见问题

Q：所以到底还要不要学编程？ 要，而且要学得比现在扎实。理由：编程是你获得 Issue Spotting 直觉的唯一途径。 你不写过 Spring Boot，就不会知道「这个接口在并发下会炸」；你不踩过序列化、事务、缓存穿透的坑，就不会知道该 review 什么。AI 能帮你写代码，但它不能替你积累踩坑的样本量。 而且面试里的技术追问，考的往往正是这些。

Q：那我该学 Python 还是继续 Java？ 继续 Java，而且加一门「AI 应用」技能栈。 理由是上一节说的：Java 渗透率 21.2%（不到 TS 的一半）、存量系统多而 Agent 覆盖差、而且 Java 的强类型约束本身就是好的 Issue Spotting 训练场。再叠上你自己的数据科学底子（Python + 建模），你的定位就很清楚了：「懂数据建模的 Java 后端 + 会做 Agent 应用」 —— 这个组合在 2027 届不拥挤。

Q：怎么在简历上体现「Issue Spotting 能力」？ 别写形容词，写「清单 + 取舍 + 验证」。 反例：「具备良好的代码审查能力」。正例：「针对 XX 模块梳理 12 项边界条件清单，实现幂等/并发/精度三类校验，测试用例覆盖 XX 场景，线上 XX 起未复现」。前者谁都能写，后者证明你真的做过。 我之前给你的简历规则里「不夸大」那条在这里依然成立——清单上每一条都必须是你真踩过或真想过 的。

Q：面试被问「你怎么用 AI」，怎么答才有分量？ 三段：① 我用它做什么（具体到任务类型）；② 我怎么验证它的产出（这是核心，讲你的检查清单、灰区反问、确定性校验）；③ 我在什么情况下不用它（这一条最能加分，因为它证明你不是在无脑崇拜）。

第三点尤其重要。面试官见过太多「AI 帮我做完了」的答案，但很少见到「这类事我不用 AI，因为错了成本太高且我验证不了」的答案。 后者才是成熟使用者的信号。

Q：我现在还早吗？ GitHub 那 40% 是全体开发者的 PR，而 Octoverse 里也提到 TypeScript/Python/Rust 都已经 40% 以上。你要是等到「所有人都准备好了」再练 Issue Spotting，那就晚了。 但也别焦虑 —— 21.2% 那行数字说明，Java 这块还有窗口，而且窗口不长。
